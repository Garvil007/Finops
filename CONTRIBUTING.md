# Contributing

## Setup

Python 3.12 or newer is required.

```bash
python -m venv .venv
. .venv/Scripts/activate      # Windows
. .venv/bin/activate          # macOS and Linux

pip install -e ".[dev]"
pre-commit install
```

Copy the environment template and set at least `LITELLM_MASTER_KEY` (it must
start with `sk-`):

```bash
cp .env.example .env
```

Nothing in the test suite needs Docker or a database. The full stack does:

```bash
docker compose up -d --build
```

## Running the checks

The four commands below are exactly what CI runs. Run them before pushing:

```bash
ruff check .
ruff format --check .
mypy src/
pytest
```

`pytest` fails under 80% coverage, the same gate CI enforces, so a local pass
means a CI pass on that criterion.

### Postgres-specific tests

Most of the suite runs on in-memory SQLite so it stays hermetic and fast. The
paths that genuinely differ between dialects -- the `finops` schema,
`date_trunc` bucketing, exact `Numeric` arithmetic -- live in
`tests/integration/test_postgres_compat.py` and are skipped unless a database is
available:

```bash
docker compose up -d postgres
export FINOPSAI_TEST_POSTGRES_URL=postgresql+asyncpg://finops:changeme@localhost:5432/finopsai
alembic upgrade head
pytest tests/integration/test_postgres_compat.py
```

CI always runs them against a Postgres service container. If you touch SQL,
run them locally too -- SQLite will not catch a Postgres-only mistake.

### Migrations

```bash
alembic upgrade head           # apply
alembic downgrade base         # reverse (CI verifies this round trip)
alembic revision -m "message"  # new revision, hand-written
```

Revisions are written by hand rather than autogenerated. Autogenerate compares
against the live database, and this project shares a server with LiteLLM's
Prisma-managed tables; `migrations/env.py` filters those out, but a hand-written
revision is the safer habit.

## Standards

- **Conventional Commits**: `feat:`, `fix:`, `docs:`, `test:`, `chore:`,
  `refactor:`, `perf:`, `ci:`. The subject is imperative and under 72
  characters; the body explains why, not what.
- **Types everywhere.** `mypy --strict` passes with no `type: ignore` unless the
  reason is written next to it.
- **Money is `Decimal`.** Never `float`. The database column is
  `Numeric(18, 8)` and it stays exact end to end.
- **Configuration comes from the environment** via `pydantic-settings`. No
  secret is ever a default, a literal, or a committed value.
- **Files stay focused**: roughly 200-400 lines, 800 as a hard ceiling.
  Functions under 50.
- **Comments explain why.** If a line needs a comment to say what it does, the
  line is the problem.

## Tests

- Arrange / Act / Assert, with those comments when the sections are not obvious.
- Test names state the behaviour: `test_untagged_spend_is_kept_as_unattributed`,
  not `test_collector_2`.
- `pytest.mark.parametrize` with `id=` for table-driven cases.
- New behaviour needs a test that fails without the change. A test that passes
  before and after proves nothing.

## Pull requests

1. Branch from `main`.
2. Make the change, with tests.
3. Run the four checks above.
4. Open the PR and fill in the template: what, why, how it was tested.
5. CI must be green. `main` is protected -- see
   [docs/dev-setup.md](docs/dev-setup.md).

## Project layout

| Path | What lives there |
| --- | --- |
| `src/finopsai/collectors/` | One module per cost source, plus the supervised run loop |
| `src/finopsai/attribution/` | Domain models, aggregation, allocation rules, forecasting |
| `src/finopsai/api/` | FastAPI app, routes, schemas |
| `src/finopsai/alerting/` | Budget evaluation and notification |
| `src/finopsai/demo/` | Simulated workloads for the demo |
| `migrations/` | Alembic revisions |
| `monitoring/` | Prometheus config and provisioned Grafana dashboards |
| `docs/` | Architecture notes, verification and demo runbooks |
